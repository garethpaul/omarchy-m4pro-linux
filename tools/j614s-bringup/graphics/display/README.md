not enable the panel, add a T6040 compatible, substitute M4 firmware, change a
version gate, or run the target.

## Why a compatibility alias is insufficient

The exact measured `/arm-io/dcp` is ASC wrapper-v6 on M3 and M4, but M4's
window is0x88000 with eight IRQs; M3 has0x6c000 and four. M2 uses wrapper-v4.
T6040's display register windows and DART apertures also differ. The machine
DART `params=0x2a2a0202`, DCP enabled mask0x800000 and existing firmware
translations were captured in the earlier read-only preflight; this lane did
not access them. A common ADT `dart,t8110` string is not proof of an identical
complete handoff.

Same-build M2/M3 DCP payloads have the same RTKit release and AppleDCP release
number, but different platform builds/hashes. The public RE specification in
ADevWithAnIdea/apple-silicon-re describes25G72/~2508, whereas these exact25G83
payloads are~2715. Neither a shared release string nor the older specification
qualifies T6040's complete RPC interface.

The selected Gravity source already implements26.6.2 for T8132. Useful source
includes `dcp.c` retained-WC mappings and startup, `iomfb_v26_6.c` callback and
method tables, and `iomfb_template.c` backlight/panel paths. The Niklas
`dcp-t8132` m1n1 tree at `b7bbf5505ffed8504d2655d28577e5bc480a0f15`
retains firmware mappings and closes AFK transports before a restartable IOP
handoff. Those operations change coprocessor state and must not be applied to
this running T6040 by analogy. They are source evidence, not a target pass.

## Actual source change

`iomfb-envelope.patch` is a zero-context export for the pinned Gravity base;
prefer the source commit. To apply the export, use `git apply --unidiff-zero`.
It adds `iomfb-packet.h` and a kernel selftest, then changes `iomfb.c` to:

- reject a callback range before reading its12-byte header;
- require header+input+reserved-output to equal the wire length within its
  32KiB channel, including the aligned nested-call end;
- copy header fields once and pass those validated values to dispatch;
- reject callback depth overflow and unsolicited ACK stack underflow;
- complete ACKs through the saved host output pointer, retaining a DMA read
  barrier before the completion consumes firmware output.

The regression compiles unchanged extracted function bodies and actual
protocol/channel declarations from each kernel source revision. Linux logging,
DMA barriers and the callback boundary are host replacements. It is not a full
kernel TU or hardware test. Baseline dispatches an invalid callback and clears
past its channel; candidate rejects without clearing output or mutating stack
state. Boundary-valid callback and zero-length ACK cases also execute the
actual receive functions. The source selftest exercises the shared helper.

The envelope-only checkpoint left callback-specific typed access unchecked.
Follow-up source8c93f2c2576b4d53d11c064f8cbd5a45095fa71d derives minimum input
and output extents from the same typed macros used by26.6 handlers. Deferred
callbacks explicitly record their eventual one-byte success output. The driver
checks these minima before clearing output, changing depth or dispatching.
Legacy firmware keeps its previous handler-table path. Additional opaque bytes
are not a complete firmware ABI pass. Transmit-side stack bounds, pointer/field
semantics and fault recovery remain outside these patches.

`typed-regression-result.json` retains an actual D006 handler/types/trampoline
regression: short declared input and zero output fail before the fix and are
rejected afterward; complete requests, bounded opaque suffixes and legacy-table
dispatch still pass under Clang ASan/fatal UBSan. `iomfb-typed-extents.patch` is
a zero-context export atop8e27e3e. `driver-regression-after-typed.json` records the
original envelope/ACK regression against the follow-up source. Neither source
patch has run on the target. The original full modular link failed on private ARM direct-map helper
references in the scanout fallback. Separate source124fd0633bb8932bbf68845ecbe8a5ffc53dfb43
now requires the existing validated no-map pool for a module and preserves the
built-in path. The complete Image and ten modules, including appledrm/asahi_m4,
link under the same configuration as that failure; [after-proof](../../infra/gravity-dcp-restricted-kernel-after.json).
No private architecture helpers were exported. Actual source host tests cover
the pool/IOVA bounds and early refusal, but no valid live J614s pool/DART handoff
or panel modesetting has been demonstrated. The subsequent source audit found
foreign PRIME imports can bypass the custom pool allocator and reach scanout.
A separate ownership restriction and actual-source boundary regression are in
progress; the successful link is not qualification to load this module.

## Exact next capture boundary

Only the primary hardware lane may perform an already approved guest session.
Recovery verification and all boot/protected-state restrictions still apply.
This document grants no target operation.

1. Arm the observer **before guest entry**. Preserve the known-good framebuffer,
   DCP firmware and DART mappings. Observe the guest's own ASC transfers at the
   ADT-derived DCP base0x402e00000. First qualify which mailbox bank and
   endpoint are actually used; do not assume that the primary four of the eight
   ADT IRQs, or an inferred extra bank, describe the full interface. Never read
   a destructive hardware OUTBOX register on behalf of the tracer.
2. Record DCP management and the guest's own endpoint startup/SET_SHMEM traffic.
   Endpoint0x37 is the selected source's IOMFB candidate, not a new T6040
   hardware result. Record the guest-published DVA and the native DART stream;
   do not select a stream solely from an enable-mask bit or replace mappings.
   A DART read helper must be qualified for these actual mappings and limited
   to independently approved RAM. Fault/unknown translation stops the capture.
3. At guest-owned IOMFB notifications, capture the bounded header and input on
   CALL and the saved output span on ACK. Keep both directions, wire word,
   context, offset, tag, input/output sizes and complete captured bytes.
   Capture the initial start-signal exchange through mode/property publication
   and one unchanged-frame presentation. Do not inject start, ACK, mode,
   brightness, sleep, or shutdown RPCs. Do not run the public `trace_dcp.py`
   wholesale: its import-time setup and generic DART assumptions have not been
   qualified for T6040.
4. Save private traces with restrictive permissions and a sidecar containing
   exact model/chip/OS and extracted firmware identity. One paused vCPU and
   repeated overlap agreement do not prove snapshot coherence: other CPUs and
   firmware may mutate memory. Independently qualify publication/cache/all-vCPU
   handling; otherwise label it a candidate capture. Preserve boot/capture IDs.
5. Export the public m1n1 CALL/ACK text format and run `dcp-transcript.py` offline.
   It rejects malformed ranges, truncated data, context mismatches, overlap,
   orphan/reordered ACKs and implicit version overrides. It reports the first
   missing handler or unmatched/undecoded structure contract, without enabling
   a device. Raw captures remain private.

The metadata sidecar keys are `chip_id`=`0x6040`, `model`=`Mac16,8`,
`os_build`=`25G83`, `dcp_payload_sha256` as above, and `dcp_build` as above.
These are caller-supplied provenance, not proof of the loaded firmware.

```sh
python3 graphics/display/dcp-transcript.py --source KERNEL \
  --metadata PRIVATE_METADATA --transcript PRIVATE_CALL_ACK_LOG \
  --scratch graphics/build-display --output PRIVATE_REPORT
```

The next driver port consumes that first exact differing contract and a
complete retained-mapping/endpoint handoff trace. Add a narrowly measured T6040
profile and callback layouts only after that evidence; then require native
connector/mode enumeration and a single known pixel presentation before
compositor,120Hz or panel power-cycle tests.
